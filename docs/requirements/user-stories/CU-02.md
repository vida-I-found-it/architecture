# CU-02 · Registrar una alerta con URLs

> **Borrador** redactado con la [plantilla](../../templates/user-story.md) a partir de [`requirements.md`](../requirements.md#cu-02--registrar-una-alerta-con-urls). Solo usa datos que el documento define; lo que no define está en **Preguntas abiertas**.

**Descripción:** el usuario elige el modo de creación, pega de 1 a 10 URLs, escribe uno o varios correos (máximo 10) a los que se les avisará, puede añadir una nota y confirma. El sistema guarda la alerta (inmutable), sus URLs y una suscripción por correo.
**Actor:** usuario fijo de la versión (sin login).
**Requerimientos cubiertos:** ALE-1, ALE-2, ALE-4, SUB-1, SUB-2, SCR-18, FE-1, FE-4, RNF-4, RNF-6, RNF-7, EJ-1, DEC-9, DEC-11, DEC-15, DEC-20, DEC-28, DEC-34.
**Reglas:** [R3](../../00-context/deliverable01.md#6--regla-de-negocio-principal) (URL peligrosa), R13 (alerta inmutable, correo enmascarado).
**Mockups:** [crear](../../design/mockups/create-alert.png) · [confirmar](../../design/mockups/confirm-alert.png).

## US-02-01 · Crear una alerta con 1 a 10 URLs y 1 a 10 correos

**Como** usuario, **quiero** pegar una o varias URLs y uno o varios correos, **para** que el sistema vigile el precio de ese producto y me avise.

| Campo | Valor |
|-------|-------|
| Requerimientos | ALE-1, ALE-2, SUB-1, SUB-2, RNF-6, FE-4 |
| Capa | 🎨🖥️ |
| Endpoint | `POST /api/alerts` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-01-AC1 | 1 URL válida y un correo válido | envío el formulario | se crea una alerta `active`, 1 URL y 1 suscripción `active`, **o nada**; `core` responde `201 Created` con `{id, status, urls[], created_at}` y ningún correo (pregunta 4) |
| US-02-01-AC2 | 10 URLs válidas y distintas | envío el formulario | se guardan las 10 URLs |
| US-02-01-AC3 | 11 URLs distintas tras normalizar | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC4 | 0 URLs | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC5 | URLs repetidas tras normalizar | envío el formulario | se guarda una sola por cada repetida: la primera aparición, en el orden en que el usuario las escribió. Normalizar es poner esquema y host en minúsculas y quitar el fragmento `#…` y la `/` final; los parámetros de consulta **se conservan** (preguntas 2 y 8) |
| US-02-01-AC6 | una alerta creada con primera URL `https://www.Tienda-A.example/p/1` | pido `GET /api/alerts/{alert_id}` | `title` y `product_name` valen `tienda-a.example`: el host de la primera URL en minúsculas y sin `www.` (pregunta 12) |
| US-02-01-AC7 | un fallo al guardar la suscripción (o cualquier otra escritura en la base: alerta, URLs, suscripciones) | envío el formulario | no queda ni la alerta ni las URLs |
| US-02-01-AC8 | una lista de correos vacía, o algún correo con formato inválido o de más de 254 caracteres (DEC-20) | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC9 | un correo con espacios y mayúsculas | se guarda la suscripción | queda normalizado (trim, NFC, minúsculas) |
| US-02-01-AC10 | 3 correos válidos y distintos | envío el formulario | se crean 3 suscripciones `active`, cada una con su correo, **o nada** |
| US-02-01-AC11 | correos repetidos tras normalizar | envío el formulario | se guarda una sola suscripción por cada repetido |
| US-02-01-AC12 | 11 correos distintos tras normalizar | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC13 | una nota de hasta 1000 caracteres, o sin nota | envío el formulario | la alerta se crea y la nota, si hay, se guarda saneada en `alert.notes` (trim, NFC y sin caracteres de control; el HTML no se elimina ni se interpreta, el largo se cuenta tras el trim); el detalle la devuelve en `notes` y el dashboard la muestra como texto ([US-07-02-AC8](CU-07.md)) |
| US-02-01-AC14 | una nota de más de 1000 caracteres | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC15 | una URL de más de 2048 caracteres | envío el formulario | se rechaza y no se guarda nada (DEC-20) |
| US-02-01-AC16 | una alerta con las mismas URLs y correos que otra ya existente | envío el formulario | se crea una alerta nueva con sus propias suscripciones; no se rechaza (pregunta 5) |
| US-02-01-AC17 | datos válidos y `schedule` sin responder tras sus 3 reintentos | envío el formulario | `core` responde 201, la alerta queda guardada con `schedule_job_id` nulo y no se revierte; el usuario no ve un error y el reintento es de [CU-03](CU-03.md) (DEC-15) |
| US-02-01-AC18 | 11 URLs de las que 2 son repetidas tras normalizar (o 12 correos con 2 repetidos) | envío el formulario | se crea la alerta con 9 URLs (o 10 suscripciones): los topes se cuentan **después** de normalizar y deduplicar (pregunta 9) |
| US-02-01-AC19 | una petición con una URL o un correo vacío o solo con espacios | la envío a `core` | 422 con el índice de ese elemento; no se guarda nada (pregunta 10) |
| US-02-01-AC20 | filas de URL o de correo vacías en el formulario | pulso «Crear» | el frontend no las envía ni las cuenta para el tope (pregunta 10) |
| US-02-01-AC21 | cualquier rechazo de validación (URLs, correos, nota, campos de más) | `core` responde | 422 con `{"error":{"code":"validation_error","message","details":[{"field","index","code"}]}}` (`index` solo en listas, base 0; `code` del catálogo de la pregunta 16); sin trazas, sin SQL y **sin repetir el valor enviado** |
| US-02-01-AC22 | una URL bloqueada en el índice 0 y un correo inválido en el índice 1 | envío el formulario | 422 con los **dos** errores en `details`, en orden modo → URLs → correos → nota (pregunta 17); no se guarda nada |
| US-02-01-AC23 | una nota vacía o solo con espacios | envío el formulario | la alerta se crea con `notes` nulo (pregunta 18) |
| US-02-01-AC24 | URLs o correos repetidos tras normalizar en el formulario | pulso «Crear alerta» | el frontend aplica la misma normalización que `core` y envía una sola de cada repetida; `core` igual deduplica (pregunta 19) |
| US-02-01-AC25 | `https://Tienda-Ñ.example:443/café` y `https://xn--tienda--b0a.example/caf%C3%A9` | envío el formulario | se guarda una sola: el host IDN pasa a punycode, el path no ASCII se codifica en porcentaje y se quita el puerto por defecto explícito (preguntas 21 y 22) |
| US-02-01-AC26 | un correo con caracteres no ASCII antes de la `@` (p. ej. `josé@correo.com`) | envío el formulario | 422 `email_invalid` con su índice; un dominio IDN después de la `@` sí se acepta (pregunta 22) |
| US-02-01-AC27 | un cuerpo con un campo que el contrato no define (p. ej. `created_by`) | lo envío a `core` | 422 `unknown_field` y no se guarda nada; `created_by` de la alerta y de sus suscripciones es siempre el usuario fijo de la versión (SUB-1, ADR-0006) |
| US-02-01-AC28 | una alerta creada con 2 correos | reviso sus suscripciones, la respuesta y los logs | cada suscripción tiene `unsubscribe_token_hash` no nulo y distinto; el token en claro no aparece en la respuesta del 201 ni en ningún log (SUB-1, RNF-7) |

### Casos borde
- URL con espacios alrededor (se recortan, AC9 y AC19); URL y correo con unicode: cubiertos por AC25 y AC26.
- Doble clic en «Crear alerta» (cubierto por US-02-03-AC3).

### Fuera de alcance
- Crear el job de captura: es [CU-03](../requirements.md#cu-03--programar-la-captura).
- Verificar que el dueño del correo lo autorizó (doble confirmación): decidida como mejora futura en DEC-14. Por ahora solo se usan correos de prueba.

## US-02-02 · Rechazar URLs peligrosas al crear la alerta

**Como** operador del sistema, **quiero** que se rechacen las URLs hacia redes internas o con esquemas raros, **para** que el sistema no descargue destinos peligrosos (SSRF).

| Campo | Valor |
|-------|-------|
| Requerimientos | SCR-18 |
| Reglas | R3 |
| Capa | 🖥️ |
| Endpoint | `POST /api/alerts` (validación interna) |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-02-AC1 | una URL con esquema distinto de `http`/`https` | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC2 | una URL `http` con puerto distinto de 80, o `https` con puerto distinto de 443 (p. ej. `http://x:443`) | envío el formulario | 422 `url_blocked` con el índice de esa URL; no se guarda nada (pregunta 21) |
| US-02-02-AC3 | una URL con credenciales (`usuario:clave@host`) | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC4 | una URL cuyo host resuelve a una IP privada o reservada | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC5 | 3 URLs, la segunda peligrosa | envío el formulario | 422 con el índice 1 (base 0) y **ninguna** se guarda |
| US-02-02-AC6 | una URL con host `localhost`, `127.0.0.1`, `::1`, `0x7f000001`, `2130706433`, `0177.0.0.1` o `[::ffff:127.0.0.1]` | envío el formulario | 422 `url_blocked` con su índice; no se guarda nada |
| US-02-02-AC7 | una URL cuyo host no resuelve en DNS, o tarda más de 2 s en resolver | envío el formulario | 422 `url_invalid` con su índice; al crear solo se resuelve DNS, no se descarga nada ni se siguen redirecciones (pregunta 20) |

### Casos borde
- IPv6 local, `localhost` e IP en decimal u octal: cubiertos por AC6.
- Host que redirige a una red interna: al crear no se sigue la redirección; lo bloquea el fetcher en [CU-04](CU-04.md).

### Fuera de alcance
- Revalidar en cada descarga y redirección: es [CU-04](../requirements.md#cu-04--capturar-el-precio-de-un-sitio); aquí solo la validación **al crear**.

## US-02-03 · Confirmar antes de crear una alerta inmutable

**Como** usuario, **quiero** que me pidan confirmar antes de crear la alerta, **para** no crear algo definitivo por error.

| Campo | Valor |
|-------|-------|
| Requerimientos | ALE-4, FE-4, FE-1 (la primera pantalla monta la base del frontend; pregunta 23) |
| Reglas | R13 |
| Capa | 🎨🖥️ |
| Endpoint | — (el modal es de frontend); sin rutas `PUT`/`PATCH`/`DELETE` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-03-AC1 | el formulario completo y válido | pulso «Crear alerta» | aparece un modal que advierte que la acción es definitiva, **antes** de enviar nada |
| US-02-03-AC2 | el modal abierto | cancelo | no se envía ninguna petición y no se crea nada |
| US-02-03-AC3 | el modal abierto | confirmo | el botón se deshabilita mientras se envía y se hace **una sola** petición |
| US-02-03-AC4 | una alerta creada | intento editarla o borrarla con `PUT`, `PATCH` o `DELETE` sobre `/api/alerts/{alert_id}` | 405 Method Not Allowed; la alerta no cambia. Lo mismo con `PUT`, `PATCH` o `DELETE` sobre `/api/alerts` (pregunta 24) |
| US-02-03-AC5 | el modal confirmado y `core` responde 201 | termina el envío | el frontend navega al detalle `/alerts/:alertId` de la alerta creada y muestra el aviso de captura de [CU-03 US-03-05](CU-03.md) (pregunta 13) |
| US-02-03-AC6 | el modal abierto | lo cierro con Escape, con clic fuera o con «Cancelar» | no se envía ninguna petición y el formulario conserva lo que escribí |
| US-02-03-AC7 | el modal confirmado y `core` responde 422, 5xx o no hay red | termina el envío | el botón se rehabilita, el formulario conserva lo escrito, no se navega y se muestra el error: junto a cada campo si es 422 (según `details`), o un mensaje general si es 5xx o red |

### Casos borde
- Cerrar el modal con Escape: cubierto por AC6. Doble clic rápido en confirmar: cubierto por AC3.
- Reintento manual tras un *timeout*: como se permiten alertas repetidas (pregunta 5) y el backend no es idempotente, puede crear una segunda alerta. Riesgo aceptado en esta versión, solo con correos de prueba.

## US-02-04 · Elegir el modo de creación

**Como** usuario, **quiero** ver el modo de creación, **para** saber que hoy se crea por URL y que la búsqueda por palabra clave llegará después.

| Campo | Valor |
|-------|-------|
| Requerimientos | EJ-1 |
| Capa | 🎨🖥️ |
| Endpoint | `POST /api/alerts` (campo `mode`) · `GET /api/alert-modes` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-04-AC1 | la pantalla de alta | la abro | el selector «Cómo quieres crearla» está visible, con «URL directa» activo y «Palabra clave» deshabilitado con el rótulo «Próximamente» |
| US-02-04-AC2 | una petición sin el campo `mode` | la envío | se trata como `url` |
| US-02-04-AC3 | una petición con `mode` = `keyword` | la envío | 422 con el código `mode_not_available` y solo ese error en `details`; no se guarda nada (pregunta 17) |
| US-02-04-AC4 | `ALERT_CREATION_MODES` con su valor por defecto (`url`) | llamo a `GET /api/alert-modes` | responde los modos y marca solo `url` como disponible |
| US-02-04-AC5 | `ALERT_CREATION_MODES` con un valor desconocido | arranca `core` | el arranque falla (pregunta 7) |

### Fuera de alcance
- Implementar la búsqueda por palabra clave con LLM (`KeywordLlmAlertSource`).
- Guardar el modo en la base: no se persiste en esta versión.
