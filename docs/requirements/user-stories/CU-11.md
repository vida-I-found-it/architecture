# CU-11 · Darse de baja de una alerta

> **Borrador** redactado con la [plantilla](../../templates/user-story.md) a partir de [`requirements.md`](../requirements.md#cu-11--darse-de-baja-de-una-alerta). Solo usa datos que el documento define; lo que no define está en **Preguntas abiertas**. Lo marcado «💡 propuesta, sin aprobar» no es una decisión. Los ejemplos usan datos ficticios.

**Descripción:** el destinatario abre el enlace de baja del correo ([CU-10](CU-10.md)), ve una página pública de confirmación (abrirla **no cambia nada**) y pulsa el botón; su suscripción pasa a `unsubscribed` y deja de recibir avisos de esa alerta. No requiere sesión. La alerta sigue activa y monitoreada.
**Actor:** destinatario del correo (sin login).
**Requerimientos cubiertos:** SUB-3, SUB-1, FE-4, RNF-4, RNF-7.
**Reglas:** R13 (correo enmascarado), DEC-13 (token), DEC-14 (sin doble confirmación; el enlace de baja es la mitigación).
**Mockups:** no existen (pregunta 9).

## US-11-01 · Abrir el enlace sin cambiar nada

**Como** destinatario, **quiero** ver una página que me pida confirmar antes de darme de baja, **para** no darme de baja por un clic accidental o por un escáner de correo.

| Campo | Valor |
|-------|-------|
| Requerimientos | SUB-3, FE-4 |
| Capa | 🎨🖥️ |
| Endpoint | página pública de baja (ruta sin definir, pregunta 2); solo lectura |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-11-01-AC1 | el enlace de baja de un correo | lo abro (GET) | veo una página mínima, sin menú ni sesión, con un botón de confirmar |
| US-11-01-AC2 | la página abierta | no pulso el botón | la suscripción sigue `active` y no hay ninguna escritura en la base |
| US-11-01-AC3 | un escáner de correo que precarga el enlace (GET) | lo abre | no pasa nada (mismo resultado que AC2) |
| US-11-01-AC4 | la página | la reviso | no muestra el correo completo (ver US-11-04-AC1) |
| US-11-01-AC5 | un enlace malformado (sin identificador o sin token) | lo abro | veo el mensaje uniforme de US-11-03 y no el botón de confirmar |
| US-11-01-AC6 | la página abierta | la reviso | tiene un título claro, el botón es accesible por teclado y los textos están en español |

### Casos borde
- Enlace con un token muy largo (miles de caracteres) o con caracteres unicode: no rompe la página ni se refleja sin escapar.
- Doble pestaña con el mismo enlace.
- El enlace abierto desde un cliente de correo que lo reescribe o lo recorta.

### Fuera de alcance
- Elegir otras preferencias (frecuencia, otras alertas): no existen.

## US-11-02 · Confirmar la baja

**Como** destinatario, **quiero** pulsar «Darme de baja» y dejar de recibir avisos de esa alerta, **para** que mi correo no siga recibiendo mensajes.

| Campo | Valor |
|-------|-------|
| Requerimientos | SUB-3, SUB-1 |
| Capa | 🎨🖥️ |
| Endpoint | `POST /api/subscriptions/{subscription_id}/unsubscribe` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-11-02-AC1 | una suscripción `active` y su token válido | confirmo | la fila pasa a `unsubscribed` (se actualiza `updated_at`); **no** se borra |
| US-11-02-AC2 | la baja hecha | la página recibe la respuesta | muestra un mensaje de baja realizada, sin el correo completo |
| US-11-02-AC3 | la suscripción ya `unsubscribed` y su token válido | confirmo otra vez | la respuesta es **igual** a la de la primera vez y no hay cambios |
| US-11-02-AC4 | una baja hecha | llega un análisis `dropped` de esa alerta | `core` no llama a `notify` para esa suscripción (US-10-01-AC3) |
| US-11-02-AC5 | una alerta con 3 suscripciones y doy de baja una | termina | las otras dos siguen `active` y reciben los avisos |
| US-11-02-AC6 | doble clic en el botón | confirmo | el botón se deshabilita mientras dura la llamada y se hace **una** petición; aunque llegaran dos, el resultado es el mismo |
| US-11-02-AC7 | falla la red o `core` responde un error | confirmo | la página muestra un error visible y permite reintentar; la suscripción no queda en un estado intermedio |
| US-11-02-AC8 | un `subscription_id` no numérico, negativo o enorme (más de 32 bits) | llamo | respuesta uniforme (US-11-03) o 422, sin error interno (pregunta 4) |
| US-11-02-AC9 | la ruta `GET`, `PUT` o `DELETE` sobre `/api/subscriptions/{subscription_id}/unsubscribe` | la llamo | no cambia nada (no existe o el método no está permitido) |
| US-11-02-AC10 | dos confirmaciones simultáneas | llegan a la vez | termina `unsubscribed` y ambas responden igual, sin error de concurrencia |

### Casos borde
- Una baja concurrente con un análisis que ya leyó la suscripción: ver pregunta 6 y CU-10 (pregunta 9).
- Suscripción cuyo `alert` está `inactive`.
- Token con espacios o mayúsculas distintas (el token es opaco; no se normaliza, pregunta 3).

### Fuera de alcance
- Volver a suscribirse (reactivar): no existe; hoy una baja es definitiva para ese correo en esa alerta (un correo nuevo requiere una alerta nueva; las alertas son inmutables).
- Dar de baja **todas** las alertas de un correo.

## US-11-03 · Rechazar tokens inválidos con una respuesta uniforme

**Como** operador, **quiero** que un token inválido, alterado o de otra suscripción no revele nada, **para** que nadie pueda averiguar qué suscripciones o correos existen.

| Campo | Valor |
|-------|-------|
| Requerimientos | SUB-3, RNF-7, DEC-13 |
| Capa | 🖥️ |
| Endpoint | `POST /api/subscriptions/{subscription_id}/unsubscribe` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-11-03-AC1 | un token alterado (un carácter cambiado) | confirmo | respuesta uniforme; la suscripción no cambia |
| US-11-03-AC2 | un token válido de **otra** suscripción | lo uso con este `subscription_id` | respuesta uniforme; ninguna de las dos cambia |
| US-11-03-AC3 | un `subscription_id` que no existe | confirmo | la **misma** respuesta (mismo código, mismo cuerpo) que en AC1 |
| US-11-03-AC4 | token vacío, ausente, de largo incorrecto o con unicode | confirmo | la misma respuesta uniforme (o 422 de validación del cuerpo, ver pregunta 4) y sin error 500 |
| US-11-03-AC5 | un token válido en una suscripción `unsubscribed` | confirmo | **no** se distingue de un token inválido por tiempo ni por contenido de forma que revele la existencia (ver pregunta 4: ¿es igual a AC1 o a US-11-02-AC3?) |
| US-11-03-AC6 | la verificación del token | se ejecuta | usa comparación de **tiempo constante** (`hmac.compare_digest` o equivalente) del SHA-256 del token con `unsubscribe_token_hash` |
| US-11-03-AC7 | la respuesta de error | la reviso | no incluye el correo, la existencia de la suscripción, el hash ni detalles internos |
| US-11-03-AC8 | un token inválido repetido muchas veces | confirmo | sigue la misma respuesta (límite de intentos: pregunta 5) |
| US-11-03-AC9 | el secreto del entorno rotado | uso un enlace ya enviado | respuesta uniforme; las bajas ya hechas no cambian (DEC-13) |

### Casos borde
- Dos suscripciones con ids consecutivos (enumeración): no deben poder deducirse una de otra.
- Token de miles de caracteres: se rechaza antes de calcular nada costoso.
- `subscription_id` con ceros a la izquierda o notación científica.

### Fuera de alcance
- Caducidad de tokens (DEC-14: «un token con caducidad» es mejora futura).

## US-11-04 · Privacidad y la alerta sigue viva

**Como** destinatario, **quiero** que la página no muestre mi correo completo y que mi baja no borre la alerta, **para** que mi dato se proteja y el dueño de la alerta siga recibiendo la vigilancia.

| Campo | Valor |
|-------|-------|
| Requerimientos | RNF-4, RNF-7, SUB-1 |
| Reglas | R13 |
| Capa | 🎨🖥️ |
| Endpoint | — |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-11-04-AC1 | cualquier estado de la página de baja | la veo | el correo no aparece completo; si se muestra, es enmascarado (formato: pregunta 7) |
| US-11-04-AC2 | un token o un enlace de baja | reviso los logs de `core`, del servidor del frontend y del proxy | el token no aparece en ninguna línea (ni en la URL registrada, ver pregunta 8) |
| US-11-04-AC3 | una baja realizada | consulto la alerta (`GET /api/alerts/{alert_id}`) | la alerta sigue `active`, con sus URLs, y sigue visible en el dashboard; el job de `schedule` no cambia |
| US-11-04-AC4 | una baja realizada | consulto la base | la fila de `subscription` sigue existiendo con su correo y `status = 'unsubscribed'` |
| US-11-04-AC5 | la respuesta de `core` | la reviso | no devuelve el correo (completo ni enmascarado, salvo decisión de la pregunta 7) ni el hash |
| US-11-04-AC6 | un fallo del servidor | ocurre en la baja | el error no filtra detalles internos |

### Casos borde
- Correo con unicode o de 254 caracteres: el enmascarado no rompe el diseño.
- El destinatario es también el dueño de la alerta, con otras suscripciones en la misma alerta: solo cambia la suya.

## Guía de implementación por repositorio

### Frontend (React)
- **Página pública** de baja (ruta y forma del enlace, pregunta 2): sin menú, sin sesión. Al abrirla **no hace ninguna petición que modifique** (US-11-01-AC2). Si necesita mostrar algo antes de confirmar, la documentación no define un endpoint de consulta (pregunta 3).
- **Acción:** el botón llama a `POST /api/subscriptions/{subscription_id}/unsubscribe` con el token (**dónde va el token: en el cuerpo, un encabezado o la ruta, no está definido**, pregunta 2). Botón deshabilitado durante la llamada; estados de carga, éxito y error visibles; textos en español vía i18n.
- No registrar el token (ni en consola ni en analítica); 💡 propuesta, sin aprobar: `Referrer-Policy: no-referrer` en esa página (pregunta 8).
- **Tests:** unitarios (el GET no llama al `POST`: AC2; botón deshabilitado: US-11-02-AC6; mensajes de éxito y de error: AC2/AC7) · integración con `core` simulado (códigos uniformes, US-11-03) · E2E: correo recibido en el SMTP de prueba → abrir enlace → confirmar → el siguiente `dropped` no genera correo para esa suscripción (QS-11).

### Core (FastAPI)
- **Endpoint:** `POST /api/subscriptions/{subscription_id}/unsubscribe`.
- **Lee/escribe:** `subscription` (`id`, `status`, `unsubscribe_token_hash`, `updated_at`). No escribe en ninguna otra tabla (no hay columna de fecha de baja).
- **Token:** `token = HMAC(secreto del entorno, id de la suscripción)`; la base guarda `SHA-256(token)` en `unsubscribe_token_hash` (`bytea NOT NULL`). `core` es el único que conoce el secreto (pregunta 11 de CU-10). Se verifica recalculando el SHA-256 del token recibido y comparando en tiempo constante.
- **Validaciones:** `subscription_id` entero acotado; token con largo máximo antes de procesar.
- **Errores:** respuesta uniforme e idéntica para id inexistente, token inválido o de otra suscripción (US-11-03). Códigos y cuerpo no están definidos (pregunta 4).
- **Idempotencia:** `UPDATE … WHERE id = :id` solo si coincide el hash; repetir devuelve lo mismo.
- **Generación del token al crear:** ver pregunta 1 (la suscripción necesita su `id`, que se genera al insertar, para calcular un token que se guarda en una columna `NOT NULL`). Afecta a CU-02.
- **Tests:** unitarios (generación y verificación del token; tiempo constante; rotación del secreto: US-11-03-AC6/AC9) · integración con PostgreSQL 16 desechable (estado `unsubscribed`, fila conservada, idempotencia y concurrencia: US-11-02-AC1, AC3, AC10; la alerta sigue `active`: US-11-04-AC3/AC4) · contrato (respuesta uniforme para los 3 casos de error, comparados byte a byte: AC1–AC3, AC5) · verificación de que ningún log contiene el token (US-11-04-AC2).

### Notify
- Solo interviene al **armar** el enlace en el correo (CU-10); CU-11 no lo llama y `notify` no debe conocer el secreto.

### Schedule
- No aplica.

### Scraper
- No aplica.

## Hallazgos de calidad

- 🔒 **Riesgo de privacidad y secreto:** el token viaja en claro en `notification.payload` de `notify` y `architecture.md` (línea 239) lista el secreto HMAC también para `notify`. Ambos contradicen SUB-3/DEC-13; ver CU-10 (preguntas 1 y 11).
- Los criterios de requirements «repetir la baja responde igual que la primera vez» y «un token inválido recibe una respuesta uniforme» solo son compatibles si la respuesta de éxito no se puede distinguir de la de error (pregunta 4).
- `POST /api/subscriptions/{subscription_id}/unsubscribe` es una ruta pública sin autenticación (decisión de la versión, §4): el único control es el token.
- No existe `unsubscribed_at`; la fecha de baja solo se infiere de `updated_at`.
