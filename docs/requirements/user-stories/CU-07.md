# CU-07 · Ver el dashboard de una alerta

> **Borrador** redactado con la [plantilla](../../templates/user-story.md) a partir de [`requirements.md`](../requirements.md#cu-07--ver-el-dashboard-de-una-alerta). Solo usa datos que los documentos definen; lo que no definen está en **Preguntas abiertas**. Todo lo marcado «💡 propuesta, sin aprobar» es una sugerencia del analista, no una decisión.

**Descripción:** el usuario ve la lista de alertas y abre una para ver el último precio por sitio, el mejor precio y las marcas de anomalía. Los datos son el último estado guardado al cargar o recargar; no hay progreso en vivo (DEC-31).
**Actor:** usuario fijo de la versión (sin login; los endpoints públicos no exigen sesión).
**Requerimientos cubiertos:** VIS-1, ALE-5, FE-4, RNF-4, RNF-6 (texto del sitio como texto), DEC-16, DEC-17, DEC-22, DEC-28, DEC-29, DEC-31.
**Reglas:** R13 (correo enmascarado), R9 y [ADR-0005](../../architecture/adr/0005-anomaly-detection-as-strategy.md) (anomalía como veredicto aparte).
**Mockups:** [dashboard](../../design/mockups/alert-dashboard.html) · [png](../../design/mockups/alert-dashboard.png). No hay mockup de la lista de alertas.
**Repos que intervienen:** frontend (React) y `core` (FastAPI). `notify`, `schedule` y `scraper` **no** participan en la lectura: solo producen los datos (CU-03 a CU-06).

## US-07-01 · Listar las alertas para poder abrirlas

**Como** usuario, **quiero** ver la lista de mis alertas, **para** abrir la que me interesa.

| Campo | Valor |
|-------|-------|
| Requerimientos | ALE-5, FE-4 |
| Capa | 🎨🖥️ |
| Endpoint | `GET /api/alerts` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-07-01-AC1 | 3 alertas guardadas | abro la pantalla de la lista | veo 3 filas, cada una con su `title` y un enlace al dashboard de esa alerta |
| US-07-01-AC2 | ninguna alerta guardada | abro la lista | veo un estado vacío claro con el acceso a «Crear alerta»; no un error |
| US-07-01-AC3 | una alerta con `status` `inactive` | abro la lista | su comportamiento sigue lo decidido en la pregunta abierta 6 (no se asume) |
| US-07-01-AC4 | `core` no responde o devuelve error | abro la lista | veo un estado de error visible y un modo de reintentar; no una pantalla en blanco |
| US-07-01-AC5 | la petición está en curso | abro la lista | veo un estado de carga visible |
| US-07-01-AC6 | una alerta cuyo `title` tiene unicode, o texto que parece HTML (`<b>x</b>`) | abro la lista | el texto se muestra tal cual, como texto, sin interpretar HTML |
| US-07-01-AC7 | cualquier alerta | consulto `GET /api/alerts` | la respuesta no contiene ningún correo completo |

### Casos borde
- Títulos muy largos (se truncan en pantalla sin romper el diseño; el límite del título no está definido, pregunta 8).
- Muchas alertas (sin paginación definida: pregunta 2).
- Doble clic sobre una fila: abre una sola vez.

### Fuera de alcance
- Crear, editar o borrar alertas (CU-02; la alerta es inmutable, ALE-4).
- Permisos por rol, búsqueda, filtros y orden configurable: el requerimiento dice «lista simple, sin permisos por rol».

## US-07-02 · Ver el detalle de una alerta con el último precio por sitio

**Como** usuario, **quiero** abrir una alerta y ver el último precio, el stock, el título y la fecha del último chequeo de cada URL, **para** saber cuánto cuesta hoy el producto en cada sitio.

| Campo | Valor |
|-------|-------|
| Requerimientos | VIS-1, FE-4, DEC-29 |
| Capa | 🎨🖥️ |
| Endpoint | `GET /api/alerts/{alert_id}` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-07-02-AC1 | una alerta con 3 URLs y un chequeo `ok` por URL | abro su dashboard | veo una fila por URL con: dominio/URL, último precio en COP, stock, título capturado, fecha del último chequeo y marca de anómalo |
| US-07-02-AC2 | las 3 URLs con precios distintos y activas | abro el dashboard | el «mejor precio» mostrado es el mínimo de los últimos precios `ok` de las URLs activas, con su sitio (DEC-16) |
| US-07-02-AC3 | la URL más barata tiene `in_stock` = `false` | abro el dashboard | esa URL **sigue contando** para el mejor precio (DEC-22) y su stock aparece como agotado |
| US-07-02-AC4 | dos URLs con el mismo precio mínimo | abro el dashboard | gana la URL de menor `alert_url_id` (el empate de `V_ALERT_BEST_PRICE`) |
| US-07-02-AC5 | una alerta con 1 sola URL con precio | abro el dashboard | el mejor precio es el precio vigente de esa URL |
| US-07-02-AC6 | una URL con `in_stock` nulo | abro el dashboard | el stock se muestra como «no informado»; no se muestra «disponible» ni «agotado» (DEC-21) |
| US-07-02-AC7 | una URL con `is_active` = `false` | abro el dashboard | no entra al cálculo del mejor precio; su presentación sigue la pregunta abierta 7 |
| US-07-02-AC8 | una alerta con `notes` | abro el dashboard | la nota se muestra como texto, sin interpretar HTML (DEC-28) |
| US-07-02-AC9 | una URL con `last_title` con HTML, unicode o texto enorme | abro el dashboard | se muestra como texto plano y no rompe el diseño |
| US-07-02-AC10 | un `alert_id` que no existe | abro `/api/alerts/{alert_id}` | `core` responde 404 y el frontend muestra «alerta no encontrada» |
| US-07-02-AC11 | un `alert_id` que no es un entero positivo (`0`, `-1`, `abc`) | pido el detalle | se rechaza sin tocar la base; el código exacto está en la pregunta abierta 4 |
| US-07-02-AC12 | el dashboard abierto y un chequeo nuevo guardado después | no recargo | la pantalla no cambia (sin *polling*, SSE ni WebSocket); al recargar muestra el estado nuevo (DEC-31) |
| US-07-02-AC13 | la petición en curso, o fallida por red/timeout/5xx | abro el dashboard | veo un estado de carga, o un error visible con reintento; nunca una pantalla en blanco |
| US-07-02-AC14 | un cliente cualquiera | llamo `PUT`, `PATCH` o `DELETE` sobre `/api/alerts/{alert_id}` | no existe la ruta o el método no está permitido (la alerta es inmutable, ALE-4) |

### Casos borde
- Alerta con la cantidad máxima de URLs (10, por CU-02).
- Precio con decimales (`numeric(14,2)`): se muestra en formato colombiano (el mockup usa `$1.099.000`); el redondeo y los decimales están en la pregunta 9.
- `list_price_cop` y `price_valid_until` existen en `V_ALERT_URL_LAST_CHECK`: si se muestran o no es la pregunta 10.
- Alerta con `schedule_job_id` nulo («sin schedule»): se comporta como una alerta sin capturas (US-07-03); el usuario no ve un error (DEC-15).

### Fuera de alcance
- Lanzar el análisis a mano desde la interfaz (`POST /api/alerts/{alert_id}/analysis`): es CU-06 (EJ-5).
- Gráfico, histórico y comparador: es [CU-08](CU-08.md).
- Dar de baja una suscripción: CU-11.

## US-07-03 · Estados vacíos: sin capturas, pendiente de primera captura y sin datos recientes

**Como** usuario, **quiero** que el dashboard me diga con claridad cuándo aún no hay datos o están viejos, **para** no confundir «todavía no» con un error.

| Campo | Valor |
|-------|-------|
| Requerimientos | VIS-1, DEC-17, DEC-31, DEC-29 |
| Capa | 🎨🖥️ |
| Endpoint | `GET /api/alerts/{alert_id}` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-07-03-AC1 | una alerta recién creada, sin ninguna fila en `alert_snapshot` | abro el dashboard | veo un estado vacío claro (no un error) y, por cada URL, el rótulo «pendiente de primera captura» |
| US-07-03-AC2 | una alerta sin capturas | consulto el detalle | no hay mejor precio; el dashboard no muestra un precio ni «0» |
| US-07-03-AC3 | una URL con chequeos pero ninguno `ok` (solo `no_price` o `error`) | abro el dashboard | esa URL muestra su último estado y no muestra precio; no se confunde con «pendiente de primera captura» |
| US-07-03-AC4 | una URL cuyo último chequeo `ok` tiene más de 24 h | abro el dashboard | la URL muestra «sin datos recientes» junto con la fecha de ese último `ok` (DEC-17) |
| US-07-03-AC5 | una URL cuyo último chequeo `ok` tiene exactamente 24 h, y otra con 24 h y 1 s | abro el dashboard | solo la de más de 24 h se marca «sin datos recientes» (límite «más de 24 h»; el reloj es inyectable en los tests) |
| US-07-03-AC6 | todas las URLs de la alerta sin precio `ok` | abro el dashboard | no hay mejor precio y se muestra el estado vacío de mejor precio, no un error |
| US-07-03-AC7 | la primera captura de una alerta nueva está en curso en segundo plano | abro el dashboard | no hay indicador de progreso en vivo (DEC-31); el estado vacío sigue hasta recargar con datos |

### Casos borde
- Alerta con 2 URLs: una ya capturada y otra pendiente (cada fila decide su propio rótulo).
- Un último `ok` antiguo seguido de una racha de `error`: la fila usa el último estado y la fecha del último `ok` (el índice `IX_ALERT_SNAPSHOT_OK` existe para eso).
- Diferencia horaria: el umbral de 24 h se compara en UTC sobre `timestamptz`; su zona de presentación está en la pregunta 3.

### Fuera de alcance
- Reintentar la captura o ver su progreso (DEC-31; SCH-9 y D11 fuera del ejercicio).

## US-07-04 · Marcar una caída anómala sin ocultar el dato

**Como** usuario, **quiero** ver una advertencia cuando el precio cae de forma sospechosa, **para** validarlo manualmente antes de confiar en él.

| Campo | Valor |
|-------|-------|
| Requerimientos | VIS-1 (marca de anomalía), DEC-18 |
| Reglas | R9 · ADR-0005 |
| Capa | 🎨🖥️ |
| Endpoint | `GET /api/alerts/{alert_id}` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-07-04-AC1 | el último chequeo `ok` de una URL con veredicto `is_anomalous` = `true` de la estrategia activa (`ANOMALY_STRATEGY`) | abro el dashboard | esa URL muestra la marca «caída anómala»; el precio **sigue visible** y no se modifica |
| US-07-04-AC2 | el mejor precio proviene de una URL marcada anómala | abro el dashboard | el mejor precio muestra junto a sí la advertencia «caída anómala, valida manualmente» |
| US-07-04-AC3 | un chequeo `ok` sin veredicto de la estrategia activa | abro el dashboard | se muestra «sin evaluar» y **no** se marca como anómalo (ADR-0005, punto 5) |
| US-07-04-AC4 | veredictos de una estrategia **anterior** (`price_anomaly` con otro `strategy` o `strategy_version`) | abro el dashboard | se ignoran; solo cuenta el veredicto de la estrategia activa |
| US-07-04-AC5 | veredictos con `reason` = `first_capture`, `insufficient_sample` o `no_dispersion` y `is_anomalous` = `false` | abro el dashboard | no hay marca de anomalía |
| US-07-04-AC6 | una URL sin chequeo `ok` | abro el dashboard | no hay marca ni «sin evaluar» (no hay nada que evaluar) |

### Casos borde
- Cambio de `ANOMALY_STRATEGY` o de versión entre dos cargas: el dashboard pasa a leer la nueva y los chequeos viejos quedan «sin evaluar».
- Dos filas de `price_anomaly` para el mismo chequeo y la misma estrategia con distinta versión: gana solo la versión activa.

### Fuera de alcance
- Calcular el veredicto: lo hace el análisis (CU-06, ADR-0005).
- Detalle numérico de la caída (p. ej. «bajó 15 %» del mockup): no está definido, pregunta 11.

## US-07-05 · Mostrar el correo siempre enmascarado

**Como** usuario, **quiero** que los correos de aviso salgan enmascarados, **para** proteger el dato personal.

| Campo | Valor |
|-------|-------|
| Requerimientos | RNF-4, RNF-7 |
| Reglas | R13 |
| Capa | 🎨🖥️ |
| Endpoint | `GET /api/alerts/{alert_id}` (y `GET /api/alerts`) |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-07-05-AC1 | una alerta con 3 suscripciones | consulto el detalle | la respuesta de `core` trae 3 correos **ya enmascarados**; ningún correo completo viaja al navegador |
| US-07-05-AC2 | cualquier respuesta de `GET /api/alerts` o `GET /api/alerts/{alert_id}` | reviso su cuerpo | no aparece ninguna cadena con el formato de un correo completo |
| US-07-05-AC3 | un correo con unicode, o de una sola letra antes de la `@` | se enmascara | no falla, no deja el correo completo y no deja la parte local vacía (el formato exacto: pregunta 5) |
| US-07-05-AC4 | una suscripción en estado `unsubscribed` | consulto el detalle | su presentación sigue la pregunta abierta 12 |
| US-07-05-AC5 | una carga del detalle (con éxito o con error) | reviso los logs de `core` y del frontend | el correo completo no aparece en ninguna línea |

### Casos borde
- Los 5 correos máximos de CU-02 caben en la pantalla sin romper el diseño.
- Dos correos con la misma letra inicial y el mismo dominio: se muestran dos entradas distintas (el enmascarado no los fusiona).

### Fuera de alcance
- Verificar al dueño del correo (DEC-14, mejora futura).
- La política de Habeas Data (D21): hasta cerrarla, solo se usan correos de prueba (condición de uso, no criterio verificable).

## Guía de implementación por repositorio

> Solo lo que la documentación define. Donde no define algo, remite a una pregunta abierta. **Ningún cuerpo de petición o respuesta está definido en los documentos** (pregunta 1): lo primero es acordar el contrato (idealmente el OpenAPI de `core`, D4) antes de que frontend y backend trabajen en paralelo.

### `core` (FastAPI)

| Aspecto | Detalle |
|---------|---------|
| Endpoints | `GET /api/alerts` (ALE-5) · `GET /api/alerts/{alert_id}` (VIS-1). Rutas de [`architecture.md`](../../architecture/architecture.md#comunicación-entre-piezas); ojo: `requirements.md` aclara que el resto del path de los endpoints no listados en la arquitectura general es «propuesta 🆕» |
| Servicio | `AlertService` (consulta y lista, según el [entregable 1](../../00-context/deliverable01.md)) |
| Lee (PostgreSQL de `core`) | `alert` (`id`, `title`, `product_name`, `notes`, `status`, `created_at`), `alert_url` (`id`, `url`, `domain`, `is_active`, `last_title`, …), `subscription` (`email`, `status`), vistas `v_alert_url_last_check` (último chequeo y último `ok`) y `v_alert_best_price` (mejor precio, DEC-29), y `price_anomaly` filtrada por `ANOMALY_STRATEGY` y su versión |
| Escribe | nada (solo lectura) |
| Mejor precio | se lee de `v_alert_best_price`; **no** hay columna materializada (DEC-29). Ver la contradicción con PRO-6 y ADR-0004 en la pregunta 13 |
| Validaciones | `alert_id` entero positivo; 404 si no existe (el [entregable 1](../../00-context/deliverable01.md) fija «enteros positivos; si no existe, 404»); sin rutas de escritura sobre `/api/alerts/{alert_id}` |
| Privacidad | enmascarar el correo **en el backend** antes de serializar (RNF-4); sin correos en logs; errores sin detalles internos |
| Texto no confiable | `last_title` y demás datos del sitio salen como texto; el saneamiento de guardado es de CU-05, pero la API no debe devolver HTML interpretable |
| Rendimiento | evitar N+1: leer las URLs, el último chequeo y los veredictos en consultas por alerta, no por URL. DEC-29 midió ~5 ms para el mejor precio de una alerta con 1.000 URLs (dato de partida, sin tráfico real) |
| Errores | formato del cuerpo de error sin definir (pregunta 1) |

**Pruebas (`pytest`, PostgreSQL 16 en contenedor desechable):**

| US-07-01-AC6, AC7 | integración | título con unicode/HTML sale como texto; ningún correo completo en el cuerpo |
| US-07-02-AC1 | integración | alerta con 3 URLs y snapshots `ok`: el detalle trae los campos esperados |
| US-07-02-AC2 a AC5 | integración | mínimo, stock agotado cuenta, empate por menor id, una sola URL |

| US-07-03-AC1 a AC6 | integración con reloj inyectable | sin snapshots, solo `no_price`/`error`, 24 h exactas y 24 h + 1 s |
| US-07-04-AC1 a AC6 | integración | `price_anomaly` con la estrategia activa, otra estrategia, otra versión, sin veredicto |
| US-07-05-AC1 a AC3, AC5 | unitaria + integración | función de enmascarado (unicode, parte local de 1 letra) y revisión de logs capturados |

## Dependencias y orden de implementación sugerido

| Depende de | Por qué |
|------------|---------|
| CU-02 | existen alertas, URLs y suscripciones que listar |
| CU-05 | guarda los chequeos en `alert_snapshot` que se leen aquí |
| CU-06 | produce los veredictos de `price_anomaly` (y, ver pregunta 13, el análisis) |
| CU-03/CU-04 | generan las capturas; sin ellas todo está «pendiente de primera captura» |
| CU-08 | comparte el endpoint de histórico y la pantalla del dashboard |

Orden sugerido (cada paso verificable):
1. Acordar contrato `GET /api/alerts` y `GET /api/alerts/{alert_id}` (preguntas 1, 4, 5).
2. `core`: lista (US-07-01) y detalle sin anomalía (US-07-02, US-07-03), con datos sembrados en `alert_snapshot` para no depender de CU-03 a CU-06.
3. `core`: anomalía y enmascarado (US-07-04, US-07-05).
4. Frontend contra un servidor simulado del contrato; luego contra `core` real.
5. E2E lista → detalle con datos sembrados.
