# CU-02 · Registrar una alerta con URLs

> **Borrador** redactado con la [plantilla](../../templates/user-story.md) a partir de [`requirements.md`](../requirements.md#cu-02--registrar-una-alerta-con-urls). Solo usa datos que el documento define; lo que no define está en **Preguntas abiertas**.

**Descripción:** el usuario elige el modo de creación, pega de 1 a 10 URLs, escribe el correo al que se le avisará y confirma. El sistema guarda la alerta (inmutable), sus URLs y la suscripción.
**Actor:** usuario fijo de la versión (sin login).
**Requerimientos cubiertos:** ALE-1, ALE-2, ALE-4, SUB-1, SUB-2, SCR-18, FE-1, FE-4, RNF-4, RNF-6, RNF-7, EJ-1.
**Reglas:** [R3](../../00-context/deliverable01.md#6--regla-de-negocio-principal) (URL peligrosa), R13 (alerta inmutable, correo enmascarado).
**Mockups:** [crear](../../design/mockups/create-alert.png) · [confirmar](../../design/mockups/confirm-alert.png).

## US-02-01 · Crear una alerta con 1 a 10 URLs y un correo

**Como** usuario, **quiero** pegar una o varias URLs y mi correo, **para** que el sistema vigile el precio de ese producto y me avise.

| Campo | Valor |
|-------|-------|
| Requerimientos | ALE-1, ALE-2, SUB-1, SUB-2, RNF-6, FE-4 |
| Capa | 🎨🖥️ |
| Endpoint | `POST /api/alerts` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-01-AC1 | 1 URL válida y un correo válido | envío el formulario | se crea una alerta `active`, 1 URL y 1 suscripción `active`, **o nada** |
| US-02-01-AC2 | 10 URLs válidas y distintas | envío el formulario | se guardan las 10 URLs |
| US-02-01-AC3 | 11 URLs | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC4 | 0 URLs | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC5 | URLs repetidas tras normalizar | envío el formulario | se guarda una sola por cada repetida |
| US-02-01-AC6 | una alerta creada | consulto sus datos | `title` y `product_name` no están vacíos y valen el dominio de la primera URL |
| US-02-01-AC7 | un fallo al guardar la suscripción (o cualquier otra escritura) | envío el formulario | no queda ni la alerta ni las URLs |
| US-02-01-AC8 | un correo vacío, con formato inválido o enorme | envío el formulario | se rechaza y no se guarda nada |
| US-02-01-AC9 | un correo con espacios y mayúsculas | se guarda la suscripción | queda normalizado (trim, NFC, minúsculas) |

### Casos borde
- URL con caracteres unicode; URL con espacios alrededor; correo con unicode.
- Doble clic en «Crear» (cubierto por US-02-03-AC3).

### Fuera de alcance
- Crear el job de captura: es [CU-03](../requirements.md#cu-03--programar-la-captura).
- Verificar que el dueño del correo lo autorizó (doble confirmación, DEC-14).

## US-02-02 · Rechazar URLs peligrosas al crear la alerta

**Como** operador del sistema, **quiero** que se rechacen las URLs hacia redes internas o con esquemas raros, **para** que el sistema no descargue destinos peligrosos (SSRF).

| Campo | Valor |
|-------|-------|
| Requerimientos | SCR-18 |
| Reglas | R3 |
| Capa | 🖥️ |
| Endpoint | `POST /api/alerts` (validación interna) |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-02-AC1 | una URL con esquema distinto de `http`/`https` | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC2 | una URL con un puerto distinto de 80 o 443 | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC3 | una URL con credenciales (`usuario:clave@host`) | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC4 | una URL cuyo host resuelve a una IP privada o reservada | envío el formulario | 422 con el índice de esa URL; no se guarda nada |
| US-02-02-AC5 | 3 URLs, la segunda peligrosa | envío el formulario | 422 con el índice 1 (base 0) y **ninguna** se guarda |

### Casos borde
- IPv6 local (`::1`), `localhost`, IP en decimal u octal, host que redirige.

### Fuera de alcance
- Revalidar en cada descarga y redirección: es [CU-04](../requirements.md#cu-04--capturar-el-precio-de-un-sitio); aquí solo la validación **al crear**.

## US-02-03 · Confirmar antes de crear una alerta inmutable

**Como** usuario, **quiero** que me pidan confirmar antes de crear la alerta, **para** no crear algo definitivo por error.

| Campo | Valor |
|-------|-------|
| Requerimientos | ALE-4, FE-4 |
| Reglas | R13 |
| Capa | 🎨🖥️ |
| Endpoint | — (el modal es de frontend); sin rutas `PUT`/`PATCH`/`DELETE` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-03-AC1 | el formulario completo y válido | pulso «Crear» | aparece un modal que advierte que la acción es definitiva, **antes** de enviar nada |
| US-02-03-AC2 | el modal abierto | cancelo | no se envía ninguna petición y no se crea nada |
| US-02-03-AC3 | el modal abierto | confirmo | el botón se deshabilita mientras se envía y se hace **una sola** petición |
| US-02-03-AC4 | una alerta creada | intento editarla o borrarla con `PUT`, `PATCH` o `DELETE` sobre `/api/alerts/{alert_id}` | no existe la ruta o el método no está permitido; la alerta no cambia |

### Casos borde
- Cerrar el modal con Escape; doble clic rápido en confirmar.

## US-02-04 · Elegir el modo de creación

**Como** usuario, **quiero** ver el modo de creación, **para** saber que hoy se crea por URL y que la búsqueda por palabra clave llegará después.

| Campo | Valor |
|-------|-------|
| Requerimientos | EJ-1 |
| Capa | 🎨🖥️ |
| Endpoint | `POST /api/alerts` (campo `mode`) · `GET /api/alert-modes` |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-04-AC1 | la pantalla de alta | la abro | el selector «Modo» está visible, con «URL directa» activo y «Palabra clave» deshabilitado con el rótulo «Próximamente» |
| US-02-04-AC2 | una petición sin el campo `mode` | la envío | se trata como `url` |
| US-02-04-AC3 | una petición con `mode` = `keyword` | la envío | 422 con el código `mode_not_available`; no se guarda nada |
| US-02-04-AC4 | `ALERT_CREATION_MODES` con su valor por defecto (`url`) | llamo a `GET /api/alert-modes` | responde los modos y marca solo `url` como disponible |

### Fuera de alcance
- Implementar la búsqueda por palabra clave con LLM (`KeywordLlmAlertSource`).
- Guardar el modo en la base: no se persiste en esta versión.

## US-02-05 · Proteger el correo del usuario

**Como** usuario, **quiero** que mi correo no se muestre completo ni se guarde en los logs, **para** proteger mi dato personal.

| Campo | Valor |
|-------|-------|
| Requerimientos | RNF-4, RNF-7 |
| Reglas | R13 |
| Capa | 🎨🖥️ |
| Endpoint | — |

### Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|----|------|--------|----------|
| US-02-05-AC1 | una alerta creada con un correo | veo cualquier pantalla de esta versión | el correo aparece enmascarado, nunca completo |
| US-02-05-AC2 | una creación de alerta (con éxito o con error) | reviso los logs de todas las piezas | el correo completo no aparece en ninguna línea |

### Nota
- Mientras la política de Habeas Data siga pendiente (D21), en esta versión **solo se usan correos de prueba**; es una condición de uso, no un criterio verificable por test.
